# ThreatCaddy 2.0.4

This client/server release fixes what a security review found in the parts of
ThreatCaddy that face the public: the hosted site, the standalone file, the
browser extension and the team server image. The app no longer runs inside a
frame, the standalone file runs only when opened from a file, whiteboards no
longer load embedded web content, and the hosted page runs no inline script but
its own. ThreatCaddy now uses no feature of a browser extension older than
1.1.3, such as the Chrome Web Store's 1.1.1, and its install links point to
the GitHub release. The team server's Compose file publishes the API on host
loopback only, `TRUSTED_PROXY_IPS` accepts CIDR ranges, and `/health` reports
only its status and version. There are no database migrations and no stored
data format changes. The extension is released at 1.1.5; this release
does not assert that a browser store has published that version.

## Upgrade

Before upgrading, save drafts and create a full backup as described in the
[2.0.2 upgrade notes](v2.0.2.md#upgrade). 2.0.4 changes no stored data format,
so 2.0.3 and 2.0.4 backups restore in either version. Ask every member of a
team to upgrade.

If you use the standalone download, save the 2.0.4 file over the 2.0.3 one,
with the same name and folder, and open it from there: some browsers, such as
Firefox and Safari, tie a local file's storage to its location, so a copy
opened from elsewhere starts empty.

If you use the hosted app, reload every open ThreatCaddy tab: a tab keeps
running the version it loaded until it reloads. **Settings → General → About**
shows the version, so you can check that each tab, and the standalone file,
runs 2.0.4.

What changes the first time you use 2.0.4:

- **The standalone file runs only from a file.** Opened from disk
  (`file://`), it works as before. Served over http or https, for example at
  `https://threatcaddy.com/threatcaddy-standalone.html` or from an intranet web
  server, it starts nothing and reads no storage. It shows a short notice with
  a link to the folder it was served from, which on threatcaddy.com is the
  hosted app. To offer ThreatCaddy from your own web server, deploy the hosted
  build (`dist/`) instead. The hosted Download links and the standalone file's
  Update button still work, because they only download the file.
- **No framing.** ThreatCaddy no longer runs inside a frame of another page,
  whether hosted or standalone. It shows a notice with an **Open ThreatCaddy**
  link that opens it in the top window. Open it in its own tab or window.
- **Whiteboard embeds become linked shapes.** Whiteboards no longer load
  embedded web content (YouTube, X, Reddit and others). When you open a board
  that has an embed, the embed becomes a rectangle that keeps its link, which
  you can open from the shape, and the board is saved that way. This is
  one-way: the embed does not come back, even if you return to 2.0.3. A pasted or
  dropped embed is converted the same way, and the Web Embed tool now draws a
  linked rectangle.
- **The community integration catalog is gone.** It fetched an unsigned file
  from a GitHub repository that does not exist. Built-in integrations, team
  templates, and importing a template from a file or pasted JSON are
  unchanged.
- **Hosted content security policy.** The hosted page now runs no inline
  script but its own, allowed by hashes the build computes; injected inline
  scripts and event-handler attributes do not run, and `raw.githubusercontent.com` is
  no longer allowed. If you build your own hosted copy, an inline script you
  add to `index.html` gets its hash at build time; one added to the built HTML
  afterwards is blocked.
- **security.txt.** threatcaddy.com publishes
  `/.well-known/security.txt`, which points to GitHub private vulnerability
  reporting, and the privacy policy says that the hosted site loads no
  analytics. Every hosted build, your own included, ships that file; if you
  serve your own copy, replace `public/.well-known/security.txt` with your own
  contact before you build (see the
  [deployment guide](../deployment.md#explicit-browser-connections-and-analytics)).
- **Browser extension 1.1.5.** ThreatCaddy now uses the extension only if it
  is version 1.1.3 or later, approved for this app. That covers CaddyAI chat,
  agents, meetings, the supervisor, chat titles and summaries, integration
  requests through the extension, web fetch and clips. Older versions, such as
  the Chrome Web Store's 1.1.1, are refused: AI requests fail with a message
  that names the version needed, integrations send their requests from the
  page as without an extension, and clips they send are not imported. Store
  1.1.1 still marks those clips "Sent" and keeps them on its Clip Review page,
  so copy what you need from there before you remove it. At the time of this
  release the Chrome Web Store still offers 1.1.1, so install 1.1.5 from this
  release's downloads:
  1. Download `threatcaddy-chrome.zip` (or `threatcaddy-firefox.zip`) from the
     [GitHub release](https://github.com/peterhanily/threatcaddy/releases/latest)
     and unzip it into a new, empty folder.
  2. In Chrome, open `chrome://extensions`, turn on **Developer mode**, choose
     **Load unpacked** and select that folder. In Firefox, load `manifest.json`
     from `about:debugging#/runtime/this-firefox` as a temporary add-on, which
     Firefox removes when it closes, until a signed build is available. The
     [manual install steps](../../extension/README.md#install--chrome) have
     the details.
  3. In the extension's popup settings, enter the ThreatCaddy address, select
     **Approve app** and accept the browser's permission prompt, then reload
     the ThreatCaddy tab.
  4. Remove the store extension, or any other older copy, and keep only the
     newest enabled: when two ThreatCaddy extensions are installed, the one
     that loads first serves the page.
- **Team server.** Upgrade the server as described in
  [deployment and upgrading](../deployment.md#6-upgrading), and check these
  first:
  - The supplied Compose file now publishes the API on host loopback
    (`127.0.0.1:3001`), for a reverse proxy on the same host. If clients reach
    port 3001 directly, set `API_PUBLISH_ADDRESS` in `.env` before you recreate
    the server: `0.0.0.0` publishes it on every IPv4 interface, or give one
    interface address. The API speaks plain HTTP, so prefer the TLS proxy (see
    [Start Services](../deployment.md#start-services)).
  - Behind a reverse proxy on the host, the server sees the Compose network's
    gateway as the peer, not `127.0.0.1`. Set `TRUST_PROXY=1` and set
    `TRUSTED_PROXY_IPS` to that gateway's address (a CIDR range now works too),
    so login lockouts and rate limits apply to each client.
    [Important Proxy Settings](../deployment.md#important-proxy-settings) shows
    how to find it. The server logs one warning, naming the peer, when a
    peer it does not trust sends `X-Forwarded-For`.
  - `/health` returns only `{"status":"ok"}` or `{"status":"degraded"}` with
    the `version`, as HTTP 200 or 503. Monitoring that read `db`, `storage`,
    `uptime`, `memory` or `timestamp` should use the status code and container
    metrics; the server log names a failing check as `Health check degraded`.
  - The application code in `/app` is read-only to the runtime user; of the
    server's own directories, only file storage (`/data/files`) is writable.
    Keep `FILE_STORAGE_PATH` on a writable volume.
  - The server deletes the generated `/data/files/.admin-secret` file once an
    administrator exists, at the first 2.0.4 startup too. A copy in an older
    backup or snapshot still works until you rotate the secret: set a new
    `ADMIN_SECRET` and restart, or use **Change Secret** in the admin panel.
  - The bot sandbox's default images are now pinned by digest
    (`python:3.12.16-slim-trixie`, `node:22.23.5-alpine3.24` and
    `alpine:3.24.4`, which replaces the end-of-life `alpine:3.19`). The server
    pulls them at startup when its Docker API can reach the registry; code runs
    never pull. If yours cannot, pull the exact references from
    [Optional Bot Runtime Settings](../deployment.md#optional-bot-runtime-settings)
    on the sandbox host first, or set `SANDBOX_PYTHON_IMAGE`,
    `SANDBOX_NODE_IMAGE` and `SANDBOX_BASH_IMAGE`.

## Security fixes

- **Standalone file:** runs only from `file://`; served over http or https,
  for example from threatcaddy.com, it starts nothing and reads none of that
  site's storage. Its content security policy now also refuses frames,
  plugins, form submissions and `<base>` changes, and loads no script from
  another site. Network connections stay open on purpose: the file connects to
  the team servers, AI endpoints, integrations and cloud storage you
  configure.
- **Framing:** the hosted app and the standalone file check before anything
  else runs whether they are framed, and show only a notice with a link to
  open ThreatCaddy in the top window, in the browser's language and colours.
- **Hosted content security policy:** no `'unsafe-inline'` in `script-src`;
  the build computes hashes of the page's own inline scripts and fails if
  `'unsafe-inline'` returns. `raw.githubusercontent.com` is no longer allowed.
- **Whiteboards:** no embedded web content is framed. Embeds become rectangles
  that keep their links, when a board is opened and when an embed is pasted,
  dropped or drawn.
- **Integrations:** the community catalog, which fetched an unsigned file from
  a repository that does not exist, is removed.
- **Browser extension:** no feature of an extension older than 1.1.3 is used,
  clips included. Store 1.1.1 has no app pairing, and its web fetch follows
  redirects and accepts private addresses. The in-app install links (help
  menu, mobile sidebar, CaddyAI banner and onboarding) point to the GitHub
  release and its install steps and say the store version is older; AgentCaddy,
  the empty chat view, Settings → AI and AI route errors say which version is
  needed. Extension 1.1.5 drops the `tabs` permission; right-click captures
  read the page's address and title through `activeTab`.
- **Team server:** CIDR ranges in `TRUSTED_PROXY_IPS`, and a warning when an
  untrusted peer sends `X-Forwarded-For`; the API published on host loopback
  by default; a smaller `/health`; read-only application code in the image,
  which no longer ships the `ssh2` test suite with its third-party test private
  keys or npm's compile cache; the generated bootstrap secret file deleted once
  an administrator exists, and rotation steps in the short-`ADMIN_SECRET`
  warning; digest-pinned sandbox images; and a version tag (for example
  `:2.0.4`) on the first verified GHCR image of each server version, never
  moved afterwards.
- **Disclosure:** threatcaddy.com publishes `/.well-known/security.txt`, the
  privacy policy states that the hosted site loads no analytics, and
  [SECURITY.md](../../SECURITY.md) lists the supported versions, the private
  reporting route, response targets and where fixes are announced. The app's
  install description and Settings → About no longer say "No server. No
  tracking." or that all data is stored locally.

## Other changes

- **Dashboard:** the default quick links add MacCrab.com and CaddyLabs.io after
  Forensicate.ai and OpenSlaw.ai. A workspace whose quick links were already
  edited keeps its own list; add them with **Add Link**.
- **CI:** the picomatch audit exception is removed, because GitHub withdrew
  GHSA-fc5q-39xc-vjpf on 18 November 2026; the reviewed-exception check stays
  for future advisories. The steps that install the test browsers' system
  packages from the runners' Ubuntu mirror have their own 35-minute limit.

## Channels and verification

| Channel | Identity to check |
|---|---|
| Hosted app and PWA | Served from the verified client build of this release's source |
| Standalone download | `SHA256SUMS`, `release-manifest.json` and the published asset digest |
| Server image | The GHCR digest and source revision in `release-manifest.json` |
| Chrome/Firefox extension ZIPs | Their own manifest version (1.1.5) and package hashes |
| Browser stores and running team servers | Checked separately; this release does not update them |

The 2.0.4 release assets are the standalone HTML file, the two extension ZIPs,
`release-manifest.json` (which records the source revision) and `SHA256SUMS`.
Download all of them before you run `shasum -c`, because `SHA256SUMS` also
covers `release-manifest.json`. threatcaddy.com serves the same client build.
The GHCR server image for this release reports version 2.0.4 in `/health`;
identify it by the digest and source revision in `release-manifest.json`, not
by a tag. It adds no database migrations. Publishing an image does not upgrade
an existing server; follow
[deployment and rollback](../deployment.md#rollback-and-restore).

The release is published with GitHub immutable-release protection, so its tag
and assets cannot change after publication; corrections need a new version.
With the GitHub CLI you can check the downloads:

```sh
shasum -a 256 -c SHA256SUMS
gh release verify v2.0.4 --repo peterhanily/threatcaddy
gh release verify-asset v2.0.4 threatcaddy-standalone.html --repo peterhanily/threatcaddy
```

Maintainers assemble and verify releases as described in
[release maintenance](../repository-maintenance.md).

## Known limitations

- The hosted content security policy still allows the cloud-storage endpoints
  that cloud backup uses (`*.s3.amazonaws.com`, `*.blob.core.windows.net` and
  `storage.googleapis.com`), and `localhost` and `127.0.0.1` on any port, for
  local AI models and local team servers. The policy alone therefore does not
  stop the page from sending data to any bucket on those services or to a
  service on your computer.
- threatcaddy.com is served by GitHub Pages, which cannot send the site's own
  response headers. It sends no HSTS header, so a first visit through an
  `http://` link can be intercepted before the redirect to https, and no
  header forbids framing; the page's own check covers framing.
- Safari and other WebKit browsers ignore a content security policy in a file
  opened from disk, so the standalone file's policy does not apply there; the
  release checks confirm it in Chromium-based browsers. Its boot checks run in
  every browser.
- Boards keep their embeds in storage, in exports and in sync until they are
  opened in 2.0.4. A teammate still on 2.0.3 still loads their content when
  opening such a board.
- At the time of this release the Chrome Web Store offers extension 1.1.1,
  which 2.0.4 refuses. In Firefox, 1.1.5 is a temporary add-on: load it again
  after each restart until a signed build is available.
- With only an extension older than 1.1.3, integrations send their requests
  from the page: a service that does not allow browser requests, or that the
  hosted content security policy does not list, fails, and the error says to
  update the extension.
- When store 1.1.1 serves the page and a newer copy is also installed, chat,
  agents and Settings → AI can show the extension as ready while every request
  is refused with a message to keep only the newest extension and reload.
- `API_PUBLISH_ADDRESS=0.0.0.0` publishes the API on IPv4 only.
- The Compose network's gateway can change when the network is recreated, for
  example after `docker compose down`; check `TRUSTED_PROXY_IPS` again
  afterwards. The warning about an untrusted `X-Forwarded-For` comes only from
  routes that use the client address, such as sign-in, not from `/health`.
- The GHCR version tag goes to the first verified build of that server
  version. Identify the release image by the digest in
  `release-manifest.json`.
- The pinned sandbox images change only when a ThreatCaddy release moves the
  pins, or when you set your own; Dependabot does not track them.
- `security.txt` expires on 17 November 2027 and must be renewed before then.
- Firefox browser tests for this release run only in CI; local release checks
  covered Chromium and WebKit.
- The [2.0.3 known limitations](v2.0.3.md#known-limitations) still apply,
  apart from the in-app install links, which now open the GitHub release.
